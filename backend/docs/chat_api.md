# Chat API

## Request

`POST /api/chat` accepts a JSON object:

```json
{
  "question": "How do I clean the filter?",
  "images": [],
  "session_id": "demo-session",
  "user_id": "demo-user",
  "deadline_ms": 20000
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `question` | string | yes | User question |
| `images` | string[] | no | Up to three PNG, JPEG, or WebP Data URLs |
| `session_id` | string | no | Generated by the server when omitted |
| `user_id` | string | no | Scopes persisted conversation context |
| `deadline_ms` | integer | no | Request deadline in milliseconds |

Example:

```bash
curl -X POST http://127.0.0.1:8002/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"question":"How do I clean the filter?","images":[],"session_id":"demo"}'
```

The response includes the generated answer, selected route, citations, related
assets, verifier result, and execution trace.

## Streaming

`POST /api/chat/stream` accepts the same request and returns server-sent
events:

```bash
curl -N -X POST http://127.0.0.1:8002/api/chat/stream \
  -H 'Content-Type: application/json' \
  -d '{"question":"The display shows an error code.","images":[],"session_id":"demo-stream"}'
```

Events describe routing, retrieval, generation, verification, and completion.
The terminal completion event contains the same response model used by the
non-streaming endpoint.

## Images

Encode images as Data URLs, for example:

```text
data:image/png;base64,...
```

The service validates the media type, encoded size, and image count before
calling multimodal providers. Provider failures degrade only the corresponding
visual capability; the text pipeline remains available.

## Conversations

Reuse a `session_id` for short-term follow-up context. Supply a stable
`user_id` only when the deployment has established an authenticated owner for
that value. Conversation history and knowledge evidence are stored separately.
